# 艺人界面与入口改版：实施设计稿

日期：2026-10-04。状态：**用户已确认布局及匹配规则；已实施并完成本地回归与浏览器验收；Docker 和真实设备边界见验收记录**。

目标：任何正常的专辑浏览入口都能直接查看艺人；候选数量与证据如实呈现；桌面用宽抽屉浏览作品，手机用整屏列表浏览。沿用 MusicBrainz 与 Cover Art Archive；资料来源继续遵循原方案的非 Wikipedia 要求。

本稿覆盖原《艺人资料与作品目录实现方案》第 4 节的入口与布局限制。需求以用户本次要求为准。实施基于已有 `codex/artist-profile-discography` 分支，核查版本 `e50f436`；先用 `git worktree list` 定位该分支，保留其他分支未提交的工作。

## 1. 已核对的问题

| 问题 | 实际原因 | 本轮处理 |
|---|---|---|
| 只有一个候选却提示多位同名 | `server/artists.py` 的 `ambiguous` 表示需要人工确认，也包含单候选证据不足；`ArtistProfile.tsx` 把该状态全部写成“有多位同名艺人” | 按实际候选数量、来源计数及证据状态分别显示；单候选直接采用，多候选通过本地专辑反向确认 |
| 单选框占据大片空间 | `base.css` 的输入框 `width:100%` 被 radio 继承；候选 CSS 仅设置 margin 与颜色 | 在艺人模块内完整限定 radio 的宽高、padding、margin 和布局占位 |
| 资料尚未查询就说暂未收录 | `profile === null` 同时覆盖未绑定、读取失败与真正资料缺失 | 按身份解析和资料读取阶段渲染；未确认时只说明需要确认 |
| 只能在按艺人分组时打开 | `ShelfPage.tsx` 分组标题有入口，普通卡片/列表/详情仍是艺人纯文字 | 新建共用艺人按钮，接入全部正常的专辑浏览位置 |
| 两端都像拥挤的表单 | 艺人仍使用通用 560px 宽抽屉，资料、候选、统计、目录及操作线性堆叠 | 增加艺人专用抽屉布局，保持其他表单尺寸 |

## 2. 推荐设计与依据

- [Bandcamp 艺人目录](https://godspeedyoublackemperor.bandcamp.com/music)：参考资料与封面目录分区、封面和作品名称的直接对应关系。桌面把资料放左侧，作品放右侧，便于连续浏览。
- [Apple Music 艺人页](https://music.apple.com/us/artist/radiohead/657515)：参考明确的艺人主标题、作品分类及标题/发行年份层级。手机改用纵向小封面列表，适合查找生涯作品及本地副本。

两端都保留碟渡现有字体、黄主色、明暗主题与收藏管理语义。视觉重点依次为艺人身份、作品目录、收藏关联；来源和更新操作按需展开。封面缺失有稳定占位，资料不足时以事实字段呈现。

交互预览有“桌面分栏 / 手机整屏 / 独立艺人入口”三种视图。封面、收藏计数均为示例，同名场景使用明确标注的虚构候选；预览确认按钮只改变预览状态。

## 3. 布局与交互

### 桌面

艺人专用宽抽屉，宽度上限约 1000px，窄桌面自动缩到可用宽度。顶部只出现一次艺人主标题与身份状态；关闭后回到原记录和焦点。

已确认时，左侧 180–220px 展示结构化资料、按启用模块显示的本地收藏摘要与来源；右侧为作品分类及自适应封面网格。作品以首次发行日期升序展示，保留当前分类口径，日期未知仍放末尾。网格根据实际内容宽度显示 2–4 列，封面尺寸约 140–190px，长标题正常换行。

待确认时，右侧改为候选核对区，作品目录等身份确认后再显示。候选整行可选：固定 18px radio、候选名称、类型/地区、存在时的别名和区分说明、证据状态、来源入口。选中后显示对应关系与“确认艺人”；调整搜索名称是次级展开操作。

### 手机

沿用现有抽屉的模态、背景锁定和关闭能力，艺人专用模式占满可用屏幕高度，顶部“返回 / 艺人”导航保持可见。使用安全区间距和单一内容滚动区；大范围正文滚动不触发头部下拉关闭。

资料浓缩为类型、地区、成立等事实行，收藏摘要占一行；更多别名、来源和更新/更换操作展开查看。作品用 56–64px 小封面纵向列表，作品标题 14px，年份与关联状态另起一行；避免为长标题做横向滚动。

候选确认使用单列完整行，名称和证据不用省略号隐藏。选择后，确认操作占用独立底栏，底部安全区内保持可达；正文滚动区为其让出真实空间，键盘展开时不遮挡搜索框。点击目标至少 44px，editable input 至少 16px。

手机布局断点沿用现有抽屉的 `840px` 约定；目录网格的列数按剩余宽度计算。预览仅示意视觉层级，不代替实际 `100dvh`、安全区、滚动和动画验收。

### 普通专辑浏览入口

| 位置 | 桌面 | 手机 |
|---|---|---|
| 库存列表 | 专辑与艺人分列，艺人单独按钮，名称清楚可见 | 小封面与专辑名组成记录主体；艺人独立一行，整行可点 |
| 库存卡片 | 专辑标题下设置独立艺人区，名称有明确动作样式 | 双列卡片同样有独立艺人区，长名称最多先展示两行，完整名称可核对 |
| 副本详情 | 艺人单独信息行，明确“查看资料与作品”的动作 | 独立的 44px 艺人动作行 |
| 售出中、交易历史、在途明细 | 每张记录中的艺人入口沿用同一组件 | 同上，艺人与金额/版本信息分行 |
| 按艺人分组 | 保留分组入口，与普通记录进入相同面板 | 同上 |

组件使用 `button type="button"`，可访问名称为“查看 {艺人名} 的资料与作品”。专辑标题继续打开该实物副本详情；艺人按钮不会触发选中副本、编辑或专辑详情。点击后再请求资料，避免每张可见卡片重复发起网络查询。

表单输入、批量表单中的选中记录摘要、回收站沿用既有职责；本轮新增入口针对正常浏览中的艺人。表单中已有的 `AlbumLine` 是选中记录摘要，不直接加入会替换当前表单的艺人导航。若以后需要支持，先定义脏表单返回流程。

进入艺人、进入关联副本、返回艺人，应保留艺人分类和滚动位置。从副本详情进入艺人也提供返回该副本的路径。复用现有返回回调，确保往返不会无限堆积回调链。

## 4. 候选与资料状态契约

复用 `ResolveResult.status`、`candidates`、`searchCount`、`evidenceComplete` 及 `ArtistCandidate.hasEvidence`，身份判定按用户确认规则调整，采用原因增加 single；复用现有 meta 映射与事务，无 schema 迁移。

| 条件 | 必须展示的内容 |
|---|---|
| 解析进行中 | “正在查找艺人…”；不展示暂未收录、多个同名或可绑定候选 |
| 1 个不同 MBID 的候选 | 直接绑定并展示“唯一候选，已自动采用”，读取资料与目录 |
| N 个不同 MBID 的候选 | “找到 N 位候选，请选择”；完整列出目前取得的候选 |
| 来源结果比已展示候选多 | 改用“已列出 N 位候选”；附“来源返回 M 项，本次尚未读取全部候选” |
| 来源总数未知 | 显示本次候选数，不声称结果只有这些 |
| `evidenceComplete === false` | “本次核对尚未完成”；保留已有候选可人工确认，不能称为唯一结果 |
| `hasEvidence === true` | “与本地专辑有匹配证据”；仍为待确认时保留人工确认步骤 |
| `hasEvidence === false` | “尚无足够的本地作品证据自动确认”；这不是错误艺人的判定 |
| `hasEvidence === null` | “作品证据尚未核对完整” |
| `not_found` 且核对完整 | “资料库暂未找到该艺人”；显示本地收藏、搜索重试 |
| 查询失败或候选空但核对不完整 | 显示查询未完成与重试，不渲染成资料库无此艺人 |
| 已绑定且资料读取失败 | 显示失败与重试；有旧缓存时同时标注旧资料，目录独立处理 |
| 已绑定、成功读取且字段缺失 | 缺失字段隐藏；概况不足可以提示资料未收录，作品仍独立展示 |
| 目录只读到部分或后续页失败 | 保留已取得的作品、显示已读取数量及失败/重试；分类数量注明是已读取数量 |

候选数是去重后的 MBID 数；`searchCount` 是来源搜索结果总数，不能称为同名人数。只有候选的实际收录名称相同，才补充“其中 X 位以相同名称收录”，并显示具体名称；否则使用“候选”。不把搜索分数显示成身份可信概率。

如果地区、类型和区分说明都缺失，显示“暂无地区与类型资料”，提供对应 MusicBrainz 艺人页核对。作品、简介或成立日期必须来自现有字段，界面不编造证据。

自动采用策略按用户本次确认更新：单候选直接采用，多候选用本地专辑与 artist-credit 反向确认，无法区分才人工选择。

## 2026-10-04 已确认的匹配与实现契约

用户明确确认：只有一个候选直接默认；多个候选通过专辑反向确认。

- 有效 MBID 去重后仅 1 位，直接保存 `single`，跳过作品与别名核对。
- 多位候选全部用本地专辑标题及 artist-credit MBID 核对，唯一有证据且其余探测未失败时自动保存 `corroborated`。
- 无证据、并列或失败则人工 fallback，显示实际候选数量；不能把检索近似结果都称作同名。
- 映射保存经 storage.py 事务，审计和备份包含采用原因；本地艺人、标题与版次字段不变。
- 旧单候选 ambiguous 缓存自动升级，旧多候选缓存重新核对；手工确认的竞争结果仍保护。
- 同一规则用于首次打开与后台预取；多候选缓存绑定本地作品标题集合，专辑变更后重新核对。独立 `ArtistButton` 由页面/详情传导航回调；脏表单中的专辑摘要保持原有行为。
